# AI辅助旅游行程规划系统 - 需求规格说明书
> 项目：AI辅助旅游行程规划系统
> 技术栈：Spring Boot + MyBatis-Plus + MySQL 8 + Vue 3 + Element Plus + DeepSeek 官方 API（deepseek-v4-pro）+ 博查（Bocha）网页搜索 API
> 文档用途：毕业设计论文【需求分析】章节及第一版系统开发、验收依据
> 版本：V1.5；修订日期：2026-10-16
> 本次调整：独立搜索切换为国内博查网页搜索 API，DeepSeek 官方 deepseek-v4-pro 继续负责资料整理与行程规划；已完成一次真实端到端调用，完整官方接口核验、自动化测试复跑及多样本评价仍待完成。

## 1 引言
### 1.1 项目背景
用户规划自助旅行时，通常需要查询景点、开放时间和门票信息，再结合日期、人数与预算安排每日活动。大模型能够理解偏好并组织行程，但普通文本生成 API 不必然具备联网能力，模型自身知识也可能过时。
本系统通过显式启用的联网检索能力获取目的地旅游资料，保存检索来源和查询时间，再调用大模型基于这些资料生成结构化行程。后端执行基础约束与费用校验，保留原始资料快照及成功方案的历史版本，便于展示、核实与追溯。

### 1.2 项目目标
1. 实现用户注册、登录、个人信息维护及个人行程管理。
2. 根据目的城市、日期、人数、预算、偏好和必去景点名称联网查询旅游资料，无需先人工录入景点库。
3. 以检索所得的候选景点和来源约束行程生成，提供可查看的来源链接及检索时间。
4. 校验生成结果的结构、日期、候选景点引用及费用汇总，支持反馈修改和成功版本留存。
5. 实现两阶段任务进度、异常处理、调用用量与费用日志，便于毕业设计演示及评价。

### 1.3 角色说明
| 角色 | 权限与职责 |
| ---- | ---- |
| 普通用户 | 注册登录、维护昵称、填写条件、生成行程、提交 AI 修改意见、查看本人方案与来源及历史版本、删除本人方案 |
| 管理员 | 登录后台、查看脱敏任务状态、阶段失败原因、调用耗时与费用日志及操作日志 |

管理员账号通过初始化数据建立；公开注册只能创建普通用户。第一版不提供管理员用户管理、景点增删改查或浏览用户完整行程和条件快照的入口。模型供应商配置通过部署环境管理，不提供网页编辑密钥功能。

### 1.4 第一版范围
1. 支持用户指定目的城市的单城市旅游规划，城市由用户输入，不要求存在于本地景点库；查询无法确认城市或城市同名有歧义时提示补充省份等信息。
2. 采用两个逻辑阶段：第一阶段后端调用独立搜索 API，并用 deepseek-v4-pro 整理资料；第二阶段使用同一模型只基于本次资料生成行程。第一版由后端按流程执行搜索，不依赖模型自主调用工具；两次模型请求均不提供搜索工具，避免新增内容绕过来源记录。
3. 景点从本次检索整理出的候选集合选择；餐饮和住宿给出区域、类型和费用建议，不承诺商家库存或可预订性。
4. 暂不包含目的地自动推荐、多城市规划、地图 API 集成、实时导航、票务预订、支付、手动逐项编辑、版本回滚及专门的版本对比页面。
5. 景点摘要、路线文案和表达优化并入规划阶段，不额外调用模型润色。无需自建爬虫、向量库或消息队列。

## 2 功能性需求
### 2.1 用户与方案管理模块
1. 注册仅收集账号和密码，账号唯一，密码采用 BCrypt 加密；不收集没有业务用途的手机号。
2. 使用服务端会话登录，退出后使会话失效；个人中心支持查看账号、修改昵称。
3. 按更新时间倒序分页展示本人方案，列表显示名称、目的城市及当前版本；每个版本不作为独立方案展示。
4. 详情按日期展示活动、费用、预算状态和来源入口；用户可以切换查看只读历史版本及对应检索资料。
5. 按方案逻辑删除，方案及全部版本从业务入口隐藏；有未结束修改任务时禁止删除。第一版不单独删除历史版本，不提供密码找回。

### 2.2 联网检索与 AI 行程生成模块（核心模块）
#### 2.2.1 输入条件
| 参数 | 必填 | 规则与说明 |
| ---- | ---- | ---- |
| 出发城市 start_city | 是 | 行程背景，第一版不安排往返目的地的城际交通 |
| 目的城市 destination_city | 是 | 用户填写城市，必要时包含省份；检索阶段确认城市身份，不依赖预建景点库 |
| 出发日期 start_date | 是 | 不早于提交当天的北京时间日期，指目的地游玩的第一天 |
| 出行天数 travel_days | 是 | 1～7 天整数，结束日期按起始日期和天数推算 |
| 出行人数 traveler_count | 是 | 1～10 人整数，费用按全部人员合计 |
| 总预算 budget | 是 | 人民币正数，最多两位小数，指全部人员的目的地费用合计 |
| 旅游偏好 preferences | 是 | 至少一项：自然风光、人文古迹、美食探店、城市休闲 |
| 出行人群 traveler_type | 是 | 单人、情侣、家庭、朋友；单人限 1 人，情侣限 2 人，家庭和朋友至少 2 人 |
| 必去景点 must_visit_names | 否 | 名称数组，最多 10 项，每项 1～100 字；检索阶段核对名称、别名及所在城市，不要求用户提供景点编号 |
| 额外备注 remark | 否 | 最多 500 字，可填写节奏、行动限制等偏好，不要求填写个人敏感信息 |

更换目的城市时提示用户重新确认必去景点名称。前后端共同校验表单，后端为准；地点真实性和归属在异步检索阶段确认，不能仅凭名称格式视为已验证。

#### 2.2.2 预算口径
1. 币种固定为人民币 CNY，包含全体人员的门票、餐饮、当地交通和住宿，不计往返目的地的城际交通、购物及其他个人消费。
2. 默认住宿晚数为出行天数减一；1 日游和最后一天住宿费为 0。住宿是全体人员房间费用合计，不直接按人数机械相乘。
3. 门票优先采用检索所得、适用范围明确的成人单人参考价，按人数计算；第一版不处理儿童、学生等优惠。来源价格区间、套票或适用条件不明确时不作为确定单价，保留原说明并按估算处理。
4. 未查到门票价格时保存未知，不能自动填 0；规划阶段须提供单人估算并明确标记为模型估算，不得冒充来源报价。餐饮、当地交通和住宿同样标记为参考估算。
5. 后端用十进制定点金额重新计算门票及分类、每日和全程费用。超预算结果可保存，但明确展示超出金额，不计为满足预算约束。
6. 来源有价格不表示实际出行日可按该价购买；总费用不代表实时成交价或完整预订报价。

#### 2.2.3 API 能力与接入要求
1. 使用 DeepSeek 官方平台；用户所称 DeepSeek_v4pro 对应本次查阅官方文档列出的请求模型 ID deepseek-v4-pro，实际请求不得使用带下划线的展示写法。
2. 按官方文档采用兼容 OpenAI 格式的 Chat Completions 协议：基础地址 https://api.deepseek.com，请求 POST /chat/completions，Authorization: Bearer 认证，model 为 deepseek-v4-pro。密钥通过 DEEPSEEK_API_KEY 等环境变量注入，不写入文档或前端。
3. 本次查阅的 Chat Completions 参数文档中 tools 仅支持 function；官方 Tool Calls 指南明确由应用实现和执行函数，模型本身不执行函数。因此不能把函数调用支持、网页端搜索按钮或模型自称联网视作 API 内置搜索能力。该判断限定于已查阅的接口，不推断其他产品或接口的能力。
4. 第一版由后端按目的地及必去名称构造查询并调用博查网页搜索 API，取得真实来源后，使用 deepseek-v4-pro 整理候选资料，再调用同一模型规划。需使用实际账号确认中文覆盖、URL 与摘要返回、额度、计费及响应时间；密钥通过 BOCHA_API_KEY 注入，不自动注册、购买或执行付费调用。
5. 两个逻辑阶段不等于两次 HTTP 请求：一次任务通常包括一个或多个搜索请求、一次资料整理模型请求及一次规划模型请求。分别记录执行与费用，不将搜索费用记为 DeepSeek 内置工具费用。
6. 后端设置 SearchProvider 和模型适配职责，统一来源、状态及用量；模型请求不提供工具，不依赖自主代理循环。搜索和模型的地址、密钥、上限与超时分开配置；日志记录实际服务商、调用类型及精确模型 ID。
7. 官方文档核对日期为 2026-10-16，同日已使用项目密钥完成一次真实闭环。文档依据：[首次调用](https://api-docs.deepseek.com/)、[Chat Completions 参数](https://api-docs.deepseek.com/api/create-chat-completion)、[Tool Calls 指南](https://api-docs.deepseek.com/guides/tool_calls)。部署前再次核对可用模型、接口与价格，单次成功不代表全部验收通过。

#### 2.2.4 第一阶段：联网检索与资料整理
1. 后端根据目的城市、日期、偏好及必去名称构造查询，联网获取景点身份、区域或地址、简介、开放说明、门票和建议时长；不把用户账号、密码或完整原行程放入搜索查询。
2. 优先使用景区、文旅部门等官方网站；不足时可采用其他公开来源，并展示来源类型。官方来源优先不等于已验证所有事实，不能仅凭模型文字标为官方。
3. 来源必须来自独立搜索 API 的实际结果，后端分配 source_id，记录标题、原始 HTTP(S) URL、来源类型、retrieved_at，以及可获取的发布时间或更新时间。资料整理请求只能引用这些 source_id；无法获得页面更新时间时为未知，retrieved_at 不表示网页内容刚更新。
4. 模型整理候选景点，后端分配本次快照内的 candidate_id，例如 C1；每个景点包含城市、名称、区域或地址、简介、建议时长及来源编号。票价、开放说明分别关联证据来源，字段缺失或仅为模型推测时明确标注，不把搜索摘要当成全文核实。
5. 合并同一地点的重复资料，保留有歧义的别名及冲突说明。必去名称逐一映射到候选编号；无法确认、重名无法消歧、不属目的城市或有明确不开放信息时，本次任务失败并列出需调整的名称，不静默替换或忽略。
6. 每个候选景点至少有一个可关联的实际检索来源，来源不足、仅有模型记忆、空结果或关键城市身份无法确认时失败，不进入规划阶段。门票和开放时间未查到可标为未知并提醒核实；来源冲突的票价不得标为确定报价。
7. 保存通过基础校验的完整候选与来源快照后进入规划，规划只能引用该快照。禁止资料整理或规划模型编造 URL 补足引用；后端检查 source_id 是否存在于实际搜索结果，URL 从搜索响应关联，不接受模型替换，但该检查不等于证明网页事实为真。
8. 第一版不主动抓取任意来源链接正文、不验证所有链接在线状态，也不跨任务复用检索缓存；每次新生成或修改均重新检索。实际搜索请求记录和来源摘要以必要范围保存，避免存储大段网页正文。

#### 2.2.5 第二阶段：结构化规划与后端校验
后端将确认后的条件、候选资料和来源编号提供给关闭搜索工具的规划请求。正常结果包含 result_type、title、summary、days；无法安排时返回 result_type 为 unable 和 reason，不产生有效版本。示意结构如下：

```json
{
  "result_type": "success",
  "title": "杭州一日人文游",
  "summary": "以本次检索资料为参考，出行前需核实价格和开放情况。",
  "days": [
    {
      "day_no": 1,
      "date": "2026-11-01",
      "activities": [
        {
          "type": "scenic",
          "candidate_id": "C1",
          "description": "参观景点并了解当地历史。",
          "duration_minutes": 120,
          "ticket_estimate_per_person": 50.00,
          "transport_advice": "可考虑公共交通，具体路线和耗时需另行确认。"
        },
        {
          "type": "dining",
          "candidate_id": null,
          "description": "在景点周边选择本地菜餐馆。",
          "duration_minutes": 60,
          "ticket_estimate_per_person": null,
          "transport_advice": "就近步行，具体路线以现场信息为准。"
        }
      ],
      "lodging_advice": "当日结束行程，无住宿安排。",
      "expenses": {
        "tickets": 100.00,
        "dining": 160.00,
        "local_transport": 40.00,
        "lodging": 0.00
      }
    }
  ]
}
```

示例 C1 仅为本次检索快照内的候选编号，不是全球景点编号；后端需关联真实来源。示例金额只说明结构，不能作为实际报价。持久化 BIGINT 编号在前后端 JSON 中统一使用字符串，候选和来源编号本身也是字符串。

保存前执行以下校验与计算：
1. 校验 JSON 解析、必填字段、类型和文本长度；活动类型限 scenic、dining、leisure，时长为正整数，每天有活动；天数、连续编号和日期与输入一致。
2. scenic 活动必须引用本次快照中的候选编号；其他活动 candidate_id 为 null。名称、区域或地址、来源链接和资料时间由后端关联快照补充，不信任规划模型另造的来源。
3. 所有必去名称对应的候选景点至少出现一次；缺失、集合外编号或来源编号不匹配时失败。候选编号校验不能发现全部文案幻觉，描述是否变相加入集合外景点需抽样人工评价。
4. 四类每日费用非负且最多两位小数，最后一天住宿为 0。scenic 活动必须有非负的 ticket_estimate_per_person，其他类型该值为 null；有明确来源单价时后端采用来源单价，否则采用模型单人估算，标记采用哪种依据。未知价格不能因程序默认值变成免费。
5. 后端按每次景点参观的所用单价乘人数重算门票，覆盖模型每日 tickets 汇总；其他三类取已校验的每日估算，活动费用不再重复累加，不推断重复参观能复用门票。
6. 汇总每日和全程费用，记录预算差额、超预算标记及估算说明。通过校验后才写入成功版本；解析、引用、必去条件、日期或金额规则失败时任务失败，不自动再调用模型修复。
7. 输出中展示来源标题、链接、查询时间和未知信息提示。交通、天气、预约、开放和价格未做实时服务验证，不声称路线最优或能够保证入园。

### 2.3 行程迭代修改与版本管理模块
1. 用户从当前成功版本发起修改，填写 1～500 字意见；不支持从历史版本分叉生成。
2. 可重新确认日期、天数、人数、预算、偏好、必去名称及备注；同一方案的出发与目的城市固定，改变城市须新建方案。
3. 结构化表单是最终约束；修改意见与预算等字段冲突时，以用户确认的字段为准，界面提示同步修改条件。新生成日期不早于提交当天，过去的历史版本仍可查看。
4. 修改任务先按新条件重新检索，再将本次资料、原版本与修改意见交给规划阶段。旧 candidate_id 仅在旧快照有效；后端通过名称与地点身份映射或保留为历史上下文，不把旧编号直接当作新候选编号。
5. 无法重新确认的必去景点导致本次修改失败；非必去旧景点可以由模型替换。成功后新增版本，保留父版本、条件快照、修改意见及本次检索快照关联。
6. 版本号从 1 连续递增；新增版本、更新当前指针与任务成功在同一事务内完成。失败不覆盖旧版、不增加成功版本号；主动重试使用新任务。
7. 版本及其成功检索快照不可变，历史版本展示当时的资料、来源和查询时间，不随外部网页或后续查询变化；保留引用摘要不意味着永久保存源网页。

### 2.4 检索来源展示与后台查询模块
1. 用户在本人成功方案中查看候选资料及引用来源；票价、开放说明标明来源或未知状态，费用估算与来源数据区分展示。
2. 来源链接仅允许 HTTP(S)，标题和摘要按文本渲染，外部链接以安全方式打开；不执行来源网页或模型返回的脚本和 HTML。
3. 管理员分页查看任务状态、当前阶段、耗时和脱敏失败原因，不默认返回用户条件、修改意见、原行程及检索资料全文。
4. 取消人工景点新增、修改、启停和预建目的地列表；检索结果用于任务快照和历史追溯，不形成需要人工维护的全局景点主数据。

### 2.5 系统日志模块
1. 每次对外 API 请求关联任务与逻辑阶段 RETRIEVAL（检索）或 PLANNING（规划），记录供应商、模型、模板版本、状态、耗时、实际 token 用量和供应商请求编号。
2. 一个任务可以有多条调用记录，使用调用类型 SEARCH、MODEL 区分；搜索 API 请求及资料整理模型请求均属 RETRIEVAL，规划模型请求属 PLANNING，搜索按实际请求或供应商返回的计费单位记录。
3. 区分搜索不可用、无结果、来源不足、来源格式无效、规划格式错误、无法安排、超时和供应商异常。前置校验失败不算模型调用；检索失败后不能再发起规划调用。
4. 费用分开记录模型 token、搜索工具及其他实际收费项，并计算可得总额。缺失用量、价格或搜索收费时标记未知或部分估算，不用 0 冒充实际费用。
5. 操作日志记录方案创建、成功新增版本和逻辑删除，不再记录景点维护操作；管理员按时间、任务、阶段和状态检索日志。
6. 默认不记录完整提示词、原始模型响应、完整网页正文、密码、会话或密钥；错误摘要脱敏。检索来源及必要引用摘要只保存在受权限控制的检索快照中，不复制到默认调用日志。

### 2.6 任务进度与异常处理模块
1. 使用单实例、数据库任务和有界后台线程池，不引入消息队列。任务状态为 WAITING、RUNNING、SUCCEEDED、FAILED；运行阶段为 RETRIEVAL、PLANNING、VALIDATING，页面分别显示“检索旅游信息”“规划行程”“校验保存”。
2. 参数校验通过后持久化任务，返回 task_id 后后台执行；前端默认每 2 秒轮询，终态停止，刷新后可恢复。个人中心显示本人近期任务及阶段失败摘要。
3. 每个用户最多一个未结束任务，首次生成和修改共同计算，并原子检查。队列满返回服务繁忙，无法入队的任务标为失败，不无限等待。
4. 首次生成成功时才创建方案及版本 1；失败保留任务与必要检索诊断但不产生空方案。修改前校验归属、未删除和基础版本仍为当前版本。
5. 用户与 request_id 组合唯一；同编号同参数返回原任务，不重复执行任一阶段，同编号不同参数返回冲突；主动重试须使用新 request_id，并重新检索。
6. 默认每用户每分钟最多受理 3 个新任务，幂等重放和前置校验失败不计入；每任务最多 2 次搜索请求，最多 16 条去重来源、24 个候选景点，每条摘要最多 1800 字符；同时控制模型输出 token 上限、总时限与供应商账户额度。
7. 连接超时默认 10 秒，检索阶段总时限默认 120 秒，规划阶段总时限默认 120 秒，整个任务执行总时限默认 240 秒（含校验保存，不含排队），均可配置；阶段内多轮工具交互共享该阶段时限，不按轮次重置。
8. 超时、工具不可用、来源不足或校验错误都转为失败；晚到响应不得继续下一阶段或写成功版本。不在后台静默改用模型记忆、自动切供应商、自动重试请求或修复生成，避免隐含费用。
9. 应用重启将遗留 WAITING、RUNNING 标为失败，不自动恢复或补跑；成功版本、当前指针和任务成功在同一事务落库。查询断网只恢复轮询，不自动重新提交。

## 3 非功能性需求
1. **易用性**：Vue 3 + Element Plus 提供条件表单、分阶段进度、失败原因、来源查看和历史版本入口，明确目的地预算范围及估算字段。
2. **可靠性**：联网执行与来源须有实际 API 记录；检索失败不得伪装成功；规划结果通过校验后才保存，修改失败保留原版本。
3. **性能**：不承诺联网和生成在固定秒数内完成。普通查询、任务受理在本地单实例、10 个并发用户演示条件下以 P95 小于 2 秒为目标，不含后台外部请求；实测分别报告检索、规划与用户总等待时间。
4. **安全与权限**：Spring Security、BCrypt、服务端会话；Cookie 使用 HttpOnly，HTTPS 下设置 Secure，写操作启用 CSRF 防护。所有方案、版本、任务、检索快照接口后端校验归属，后台校验管理员角色。
5. **外部内容边界**：用户备注、搜索摘要和网页内容仅作为资料，不能覆盖系统规则、要求泄露密钥或触发额外工具。仅开放旅游检索所需工具，不根据外部文本执行指令；SQL 参数绑定，前端不执行模型 HTML。
6. **密钥与配置**：供应商密钥通过环境变量或不提交版本库的本地配置注入，不下发前端、不写日志；记录所用模型和工具配置版本以便复现。
7. **可维护性与扩展性**：Controller、Service、Mapper 分层，搜索适配、模型适配、来源归一化、结果校验和任务调度职责清晰；分别验证 DeepSeek 官方 deepseek-v4-pro 和待选搜索 API，平台差异通过适配层处理。
8. **部署**：单实例本地演示、前后端同源反向代理；多实例调度、高可用和跨实例限流不纳入第一版。

## 4 业务核心流程
### 4.1 首次生成
1. 用户填写城市、日期、人数、预算、偏好和可选必去名称，确认预算范围及联网用途。
2. 后端校验参数、幂等、限流和并发，保存条件，创建 WAITING 任务并返回编号。
3. 后台进入 RUNNING / RETRIEVAL，由后端执行独立搜索 API 查询，再调用 deepseek-v4-pro 整理候选；核对来源、地点归属及必去映射，保存检索快照。
4. 资料可用后进入 PLANNING，关闭搜索工具，基于本次候选生成 JSON；无可用资料则失败，不规划。
5. 进入 VALIDATING，校验结构、日期、必去景点与来源，重算费用、补充引用及估算标记。
6. 同一事务创建方案与版本、关联检索快照、更新任务成功；前端展示行程、来源、检索时间和预算状态。失败显示具体阶段原因，不展示为有效方案。

### 4.2 修改与历史查看
1. 用户从当前版本提交修改意见和重新确认的表单，后端校验权限及基础版本。
2. 新任务重新检索，按新快照映射景点再规划，沿用相同校验和保存流程。
3. 成功新增版本，失败保留旧版；查看历史时读取其原快照，不重新搜索或覆盖来源。
4. 无未结束修改任务时用户可逻辑删除方案；管理员仅查看授权范围内的任务诊断和日志。

### 5.5 检索快照表 search_snapshot
| 字段名 | 类型 | 说明 |
| ---- | ---- | ---- |
| snapshot_id / task_id | bigint | 自增主键、所属任务；task_id 唯一 |

| search_context | JSON | 本次实际采用的查询词或供应商返回的可得查询信息、检索日期、适配配置版本；未提供的内部查询标未知 |
| candidates_json | JSON | 候选编号、名称、城市、区域或地址、简介、建议时长、票价、开放说明、字段来源编号与不确定性说明 |

票价未知保存 null，明确来源价、模型估算与未知状态分开；候选单人模型估算在规划结果中存储，不反写检索来源。候选和来源编号仅在此快照内有效，引用由（snapshot_id，candidate_id/source_id）共同确定。仅保存通过检索基础校验的快照，一次写入后不可变；之后即使规划失败也可保留，失败诊断使用脱敏日志，不保存无效结果伪装有效快照。

### 5.8 数据关系与一致性
1. 用户与方案、任务一对多；方案与版本一对多；任务最多一个有效检索快照和一个成功版本，与调用日志一对多。版本引用同任务的快照，历史资料不可覆盖。
2. 对方案归属与更新时间、任务归属与状态、调用日志任务与阶段及时间建立索引；方案版本号、用户请求编号、快照任务编号和版本任务编号设唯一约束。
3. 当前版本、父版本必须属于同一方案；成功版本、指针和任务状态原子保存，写入前再次检查任务仍未失败。
4. 所有快照入口校验任务归属和所关联方案未删除；逻辑删除后，版本、来源与任务结果入口均不得继续泄露内容，状态接口仅返回方案已删除提示。
5. 管理员诊断接口不返回输入、原行程或完整检索快照。时间按北京时间展示，日期 YYYY-MM-DD，金额用十进制类型；不因来源 URL 可公开访问而放开整份用户快照权限。

## 6 接口需求简述（后端）
以 /api 为前缀，JSON 为主，BIGINT 编号统一以字符串返回。注册和登录公开；其余普通业务接口需登录，后台接口需管理员角色。

| 方法与路径 | 用途与主要规则 |
| ---- | ---- |
| POST /api/auth/register | 注册，账号与密码，角色只能为普通用户 |
| POST /api/auth/login | 登录建立会话 |
| POST /api/auth/logout | 退出并使会话失效 |
| GET /api/users/me | 查看本人账号与昵称 |
| PATCH /api/users/me | 修改本人昵称 |
| POST /api/plans/generate | 提交条件、must_visit_names 和 request_id；返回 task_id，不等待搜索或规划完成 |
| POST /api/plans/{plan_id}/revisions | 提交 base_version_id、确认的条件、修改意见与 request_id，返回 task_id |
| GET /api/tasks | 分页查询本人近期任务、阶段与脱敏失败摘要 |
| GET /api/tasks/{task_id} | 查询状态和阶段；成功返回 plan_id、version_id，失败返回阶段错误，不返回整份输入 |
| GET /api/tasks/{task_id}/research | 查看本人任务已形成的检索快照与来源；未形成时返回资料暂不可用；关联方案已删除时拒绝访问 |
| GET /api/plans | 分页查询本人未删除方案 |
| GET /api/plans/{plan_id} | 查看当前成功版本及来源入口 |
| GET /api/plans/{plan_id}/versions | 查询本人方案历史版本列表 |
| GET /api/plans/{plan_id}/versions/{version_id} | 查看所属版本的行程、来源、检索时间及估算标记 |
| DELETE /api/plans/{plan_id} | 逻辑删除，无未结束修改任务时允许 |
| GET /api/admin/tasks | 分页查看任务状态、阶段、耗时和脱敏错误，不含条件或内容快照 |
| GET /api/admin/api-logs | 分页查询两阶段调用、用量、搜索收费和错误日志 |
| GET /api/admin/operation-logs | 分页查询操作日志 |

不再提供预建目的地列表、景点查询或管理员景点维护接口。所有列表有分页或受控上限；新任务受理返回 202，参数错误 400，未登录 401，后台角色不足 403，不存在或不属于本人 404，幂等参数冲突、未结束任务、基础版本过期或检索快照尚不可用 409，限流 429，队列繁忙 503。任务内的搜索与规划错误由任务失败状态返回，不将异步接口错误假装成成功行程。错误响应含 code、message、请求追踪编号，不暴露堆栈、密钥或原始提示词。

## 7 系统约束
1. 系统为毕业设计演示项目；联网检索也不能保证价格、开放、天气或预约实时准确，页面提醒出行前核实。
2. 第一版以人民币预算的国内单城市旅游为演示场景，覆盖程度取决于所选搜索 API 和公开资料，不能保证任意地点都有足够信息。
3. 不支持实时地理距离计算、地图路线及交通时刻校验；交通仅为建议，后续可扩展地图 API，第一版不依赖它。
4. 有效版本代表通过基础结构、引用关系和费用计算校验，不等于来源事实全部正确或路线最优；网页内容可能变化或失效。
5. 搜索工具必须有真实执行证据和可追溯来源；没有来源、无法搜索或来源不足时失败，不降级成无来源攻略。
6. 调用依赖网络、配额和供应商服务；接入前验证能力、余额及计费，开发和演示记录供应商配置与版本。
7. 提交前说明：必要出行条件和待整理资料会发往 DeepSeek 官方 API，城市、日期、偏好和必去名称等必要查询条件会发送给独立搜索供应商；不把完整原行程或账号信息作为搜索查询。避免输入身份、证件或联系方式，不发送账号密码和会话信息。
8. 搜索结果及模型输出都作为不可信外部内容处理，只用于旅游资料和行程生成，不产生执行代码、修改系统配置或扩大工具权限的能力。

## 8 可行性分析
### 8.1 技术可行性
后端使用 Spring Boot、Spring Security、MyBatis-Plus 和 MySQL 8，前端使用 Vue 3 与 Element Plus。使用 OkHttp 调用 DeepSeek 官方 https://api.deepseek.com/chat/completions，model 为 deepseek-v4-pro；另接独立搜索 API 获取资料。后台线程池顺序执行检索和资料整理、行程规划两个逻辑阶段，数据库存任务、快照、版本与日志，前端轮询进度，无需本地部署模型。
官方文档已确认模型 ID、地址及函数由应用执行的边界，且已完成一次博查搜索、DeepSeek 资料整理、规划与保存的真实闭环，初步证明该样本可运行。完整官方接口核验、版本与异常测试、来源人工抽查和多样本评价仍需继续。主要难点是来源可靠程度、名称消歧、价格未知、两类服务费用及事务一致性，不能仅凭单次成功声称全部指标已经达标。

### 8.2 经济可行性
使用可本地部署的开源组件；DeepSeek 官方模型费用依其当前政策，独立搜索 API 费用依搜索供应商政策，分别核对价格和额度。预估每任务费用时汇总资料整理和行程规划的所有模型请求，以及实际搜索请求或搜索计费单位，避免将每个任务当作一次普通生成请求或假定官方模型费用包含搜索。
保存价格币种、单位和记录日期；采用可配置超时、任务限流及供应商额度管理控制演示成本。检索后失败或规划失败也计入已发生费用，用量缺失时说明未知，不将未完成任务一律按零成本处理。

### 8.3 操作可行性
用户填写城市和可选必去名称即可生成，无需先维护景点库。界面显示检索、规划与校验进度，结果提供来源入口和未知信息说明；管理员主要查看任务、调用与费用异常。演示前验证联网能力，准备可查询城市和异常样例；模拟结果须明确标为测试，不作为真实联网演示证据。

## 9 验收与评价标准
### 9.1 功能与异常验收
| 场景 | 预期结果 |
| ---- | ---- |
| 无本地景点库生成 | 新输入的可检索城市可直接联网生成，无需管理员预录；保存两个阶段的关联记录和来源 |
| 真实联网能力 | 有后端独立搜索 API 的请求记录和实际来源元数据，不能以 DeepSeek 生成文字或声明联网判定搜索成功；搜索不可用时失败 |
| 两阶段隔离 | 检索资料校验完成才规划，规划阶段关闭搜索，不新增无记录来源；进度可区分阶段 |
| 必去名称与城市消歧 | 名称逐一解析映射，重名、不属目的地、查无资料或明确不开放时说明原因，不静默替换 |
| 来源缺失或编造 | 无来源、引用不在工具返回中或候选缺来源时失败；不能进入规划补写虚假链接 |
| 检索无结果与限额 | 显示检索失败原因，不调用规划、不创建空方案，也不降级为模型记忆回答 |
| 信息时间与冲突 | 检索时间和页面时间分开，未知不伪造；冲突与缺失明确提示，官方优先不冒充事实全面验证 |
| 门票未知与费用依据 | 未知不默认免费；采用模型估算时明确标识，有可适用来源价时采用来源价；全部人员费用与预算差额正确 |
| 预算与住宿 | 超预算可保存且明确标记；1 日游和最后一天住宿为 0，排除往返目的地交通，不重复累计活动费用 |
| 规划输出异常 | JSON、日期、字段、引用、必去景点或金额不合规则失败，不自动修复调用，不产生有效版本 |
| 各阶段超时与晚到 | 检索或规划超时立即失败，晚到结果不能进入下一阶段或写成功版本，总执行时限覆盖校验保存 |
| 重复提交 | 同用户同 request_id 同参数只执行同一任务，每个逻辑阶段不会因重复点击额外运行；冲突参数返回 409 |
| 并发、限流和队列满 | 一用户一个未结束任务，限流 429，队列忙 503，不遗留无限等待任务 |
| 修改与重新检索 | 新版本使用新快照，候选编号不跨快照混用；失败保留原版，成功才连续增加版本号 |
| 历史与来源变化 | 后续查询或外部网页变化不覆盖旧快照，历史继续展示当时摘要、来源及查询时间 |
| 删除与越权 | 删除后方案、版本、来源和任务结果入口都不可泄露内容；用户不能访问他人快照，普通用户不能访问后台 |
| 服务重启 | 遗留未结束任务失败不补跑；已成功提交的版本、指针和任务状态一致 |
| 外部恶意文本 | 网页摘要中的指令不覆盖系统规则，不执行代码、泄露密钥或启动额外工具；前端不执行模型 HTML |
| 成本与日志 | 检索和规划分别记录，搜索收费不遗漏；未知用量和费用明确标注，失败任务已发生费用仍统计，无敏感原文日志 |

### 9.2 评价样本与统计口径
1. 至少 10 组固定条件，每组独立执行 3 次，覆盖不同城市、天数、人数、预算和偏好，形成至少 30 个真实端到端任务；记录测试日期、模型、提示词与工具配置、来源及检索快照。在线检索结果会变化，快照用于解释差异，不承诺输出完全可复现。
2. 正常首次生成与修改分别报告；测试工具不可用、畸形返回、假来源、超时及越权可用模拟接口，模拟异常不混入真实联网质量样本。
3. 幂等重放不算新任务，主动重试算新样本；受理后检索失败的正常样本不能从端到端成功率分母中剔除。另可固定检索快照反复测规划质量，但须与真实端到端测试分组。

| 指标 | 定义与统计方法 |
| ---- | ---- |
| 检索可用率 | 形成通过校验快照的任务数 ÷ 实际启动检索的任务数；无结果、工具失败、超时及来源不足都计失败 |
| 来源关联完整率 | 成功快照中景点身份至少关联一个真实工具来源的候选数 ÷ 成功快照候选总数；另报告人工核实来源是否支持所引事实的样本通过率，不以链接存在代替事实正确 |
| 规划结构化输出成功率 | 满足成功 JSON 字段和类型的结果数 ÷ 实际启动规划的任务数；规划超时、无法安排和格式错误计入分母，不计分子，检索失败未规划的任务另列 |
| 端到端基础约束满足率 | 成功保存且满足日期、候选引用、必去映射和费用规则的任务数 ÷ 同批实际启动检索的任务数；超预算可通过基础校验 |
| 预算满足率 | 成功保存且总费用不超预算的任务数 ÷ 同批实际启动检索的任务数；失败及超预算不计分子 |
| 人工评价 | 抽查来源能否支持名称、城市、门票和开放说明，另查活动节奏、集合外文案、交通建议和偏好符合情况；修改样本评价意见落实，逐项报告样本数与失败例 |
| 阶段耗时 | 按 RETRIEVAL 和 PLANNING 分别汇总阶段耗时，含阶段内多轮交互，报告平均值、P95 与超时数；每次请求耗时另由日志统计，不把请求数当任务数 |
| 用户等待时间 | finish_time 减 create_time，包含排队、检索、规划、校验保存，对全部已结束样本报告平均值和 P95 |
| 调用与任务成本 | 调用费用包含 token、搜索和其他适用收费；按任务汇总所有实际阶段。完整费用样本计算均值，同时报告样本覆盖率、部分费用和未知数；失败已发生费用计入 |

报告分子、分母、有效样本数和环境；P95 采用排序后向上取整的最近秩方法。不同供应商、模型及币种分组报告，不把缺搜索费用的 token 成本当完整任务成本，也不把未知填零。

### 9.3 文档与系统一致性验收
1. 功能、流程、数据表、接口和异常验收均对应两阶段架构，取消人工景点库依赖及相关接口；目的地和必去名称无需先关联本地景点编号。
2. 前端技术、单城市范围、预算口径、版本留存及权限保持一致；来源记录、工具实际执行、时间与成本有明确数据依据。
3. 文档采用 UTF-8 中文 Markdown，表格列数一致，示例 JSON 可解析，候选编号按快照作用域关联；未验证供应商能力和价格不写成既成事实。
